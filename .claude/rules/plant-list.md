# Plant List

## Search (#512, product ADR-0055)
**Plant List search** (#512, product ADR-0055) — a top-bar search icon expands the app bar in place (`[back arrow] [field] [clear ✕] [Sort]`, Settings hidden), never a persistent search row; shown only when `rooms.isNotEmpty() || hasUnassignedPlants` (mirrors the room-chip row's own gate — both are true iff the user has ≥1 active plant), and stays open once opened regardless of that count. Matching (`ui/screens/plantlist/PlantSearch.kt`'s `matchesSearchQuery()`, a small pure function, unit-tested in isolation) is a case-insensitive, accent-folded (`java.text.Normalizer` NFD + strip combining marks, no new dependency) substring of the trimmed query against `Plant.name` **or** `Plant.species` — never `room`/`notes`. The query is deliberately **not** an input to `PlantListViewModel`'s DB-bound `plantsWithStatusBeforeSearch` combine (room filter → `buildStatus()`'s per-plant Room queries → `applySortOrder()`) — `plantsWithStatus` is a second, cheap downstream `combine` that just `filter{}`s those already-built, already-sorted statuses by the query, so typing/clearing never re-runs a single Room query (a query fed into the DB-bound combine directly was a real, shipped-then-fixed bug: every keystroke re-queried every room-filtered plant). It still composes correctly with the room chips and every sort option's own filtering (`BOTH_DUE`/`CARED_FOR_TODAY`/`ACTIVE_ISSUES`), since the predicate is per-plant and commutes with both; a non-blank query with zero results shows a dedicated empty state ahead of every sort/room-based empty message. Search state (`searchQueryText`/`isSearchActive`) is in-memory only, same ViewModel-scoped lifetime as `selectedRoom` — survives Plant Detail → back, resets on process death, no DataStore key. `searchQueryText` is a synchronous `var … by mutableStateOf("")` for the TextField (the `AddEditPlantViewModel` precedent — avoids driving a field off an asynchronously-collected `StateFlow`) written by the same `setSearchQuery()` setter that also updates the private `MutableStateFlow<String>` the `combine` reads, so the two can't drift; auto-focus on a fresh tap of the search icon (not when search was already open, e.g. returning from Plant Detail) is a plain consumed-once `pendingSearchAutoFocus` field (mirrors `PlantDetailViewModel`'s `pendingNewLogCareType`/`consumeNewLogCareType()`), not a `Flow`, since a `SharedFlow` emission can race the `LaunchedEffect` collector that would receive it. Selection mode's contextual bar replaces the search bar exactly as it replaces the normal bar (search stays applied underneath); system Back exits selection first when both are active.
