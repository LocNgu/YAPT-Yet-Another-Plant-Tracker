# Repotting

## Seasonal repot planning (#809, product ADR-0057)
**Seasonal repot planning** (#809, product ADR-0057, amending product ADR-0022's due-date rule) — two independent features, both unset by default so every due date stays as it was. A **one-off plan** is `Plant.repotPlanSeasonStartAt` (the target season's first day at start of day, system zone — a timestamp, so a timezone/hemisphere change never moves the due date; the label is derived) plus `repotPlanMadeAt` (`updatedAt` changes on every edit, so it can't serve); **preferred seasons** for the recurring interval are `Plant.repottingSeasons` (`SeasonalFertilizing.encode`/`decode`, `null` = every season = unconditional early-out). Pure rules in `SeasonalRepotting` (`domain/schedule/`, details in `.claude/rules/schedule.md`): the nearest-preferred-stretch shift (time-stable: a function of the raw date only, never of today, so a shifted date may land in the past and reads overdue until repotted; a candidate less than half the interval after the last repot (or `createdAt`) falls forward to the next stretch), the picker's `upcomingSeasons()`, `resolvePlan()`, and `repotLogClearsPlan()`. `CareSchedule.computeStatus()` lets a plan **win outright** over the interval date (even earlier, no interval needed — deliberately unlike product ADR-0039's defer-only `maxOf` override): `isRepottingDueSoon` for the whole season, `isRepottingOverdue` only from the day after it ends, told apart by `PlantCareStatus.repottingPlanSeasonEndAt` (non-null exactly for a plan, alongside `repottingPlanSeason`, resolved with the status's own hemisphere so copy can't name a different season than the due state used). A newly inserted REPOT log clears the plan when its local day is on or after the plan-made day (a backdated one leaves it) via the shared `RepotPlanReset.clearIfSuperseded()`, called from both `QuickLogUseCase` and `AddCareLogViewModel` *after* `WateringLifecycleReset.applyRepotReset()` (its full-row write of the plan it just read would otherwise put a cleared plan back; `QuickLogUseCase.maybeApplyRepotReset()` re-reads the plant fresh first, as `AddCareLogViewModel` does, because its callers pass possibly stale snapshots) and writing through the column-specific `PlantDao.updateRepotPlan()`; editing/deleting a REPOT log never clears or resurrects a plan. `AddEditPlantViewModel.saveEdit()` builds a fresh `Plant`, so every new `Plant` column must be carried over from `existing` there. Surfaces: the daily notification says "Repot planned this spring" in season and "Planned repot overdue by N days" after it, N counted from the season's last day (never the plan start — `ReminderNotificationComposer`'s `RepottingPlannedThisSeason`/`RepottingPlanOverdue`); `TodayQueueAggregator` buckets/orders a plan's Care task by its season state (season start while upcoming, today while in season → Today, the season's last day once ended → Overdue), never by the raw past start date, and the REPOT tile shows "Planned for spring" as its second line. Shipped as three PRs (data + domain + ADR; the reminder/Care surfaces; then the UI). **UI**: Plant Detail's Repot tab has a "Plan repot" outlined button beside the "Repot" quick-log (`PlantDetailTabActionRow`'s optional `TabSecondaryAction`; hidden while a plan exists, since Edit lives on the plan line) opening `RepotPlanSeasonDialog` — an `AlertDialog` of `SeasonalRepotting.upcomingSeasons()` (the Reschedule dialog's presentation, never chips: product ADR-0023). `RepotPlanSummary` (`RepotPlanSection.kt`) shows "Planned: spring 2027" with Edit/Clear (label from `SeasonalRepotting.resolvePlan()` on the stored timestamp, one whole sentence per season via `repotPlanLabelRes()`) or, with no plan, the next interval date (`DateUtils.formatDate`) and the preferred seasons when not all four — nothing at all with neither a plan nor an interval. `setRepotPlan()`/`clearRepotPlan()` (`PlantDetailRepotPlanActions.kt`) write only the plan columns through `PlantRepository.setRepotPlan`/`clearRepotPlan` but run inside `plantEditMutex`, so a concurrent full-row writer (each re-reads the plant fresh inside that lock) can't put a stale plan back; `now` is a defaulted parameter, not an injected clock. Add/Edit Plant reuses `FertilizingSeasonsSelector` (a new `labelRes` parameter; the repotting-specific snackbar copy is passed by the screen through the existing `onLastSeasonLocked`) under the repotting slider, only while the reminder is on, bound to `AddEditPlantViewModel.repottingSeasons`/`toggleRepottingSeason()` (a toggle, per #804). `repottingSeasons` is saved as-is even with the reminder off — inert without an interval, but toggling the reminder back on doesn't forget the choice; the plan itself is carried over from `existing` in `saveEdit()`, never edited there.

## Repotting overview (#525, product ADR-0059)
**Repotting overview** (#525, product ADR-0059; delivered as two PRs — data/domain #864, then the UI #865) — an audit page, never a sort option, Care task, or notification, for active plants not repotted in a long time. Entry is a Settings row ("Repotting overview") directly after Plant Graveyard, nested like Graveyard (`Screen.RepottingOverview`, route `repotting_overview`, bottom bar hidden, back arrow `cd_back`, Back returns to the Settings tab). The row's subtitle is a plural count for the **saved** chip ("4 plants not repotted in 2+ years" / "3 plants never repotted", one neutral "No plants to review" for zero whatever the chip; `RepottingOverviewThreshold.settingsSubtitleRes()`). **One pipeline feeds both**: `observeRepottingOverview()` (`domain/repotting/`) combines active plants, `CareLogRepository.observeLastCareAtByPlant(REPOT)`, the saved threshold and a day-change flow through the pure `RepottingOverviewBuilder`, and both `RepottingOverviewViewModel` and `SettingsViewModel.repottingOverviewSummary` call it, so the page's list and Settings' count can't drift. The page VM constructor-injects `dayChange: Flow<LocalDate> = dayChangeTicker()` (#550 — its tests pass a non-real ticker, the midnight test drives a `MutableSharedFlow`, never `advanceUntilIdle()` against the real one); `SettingsViewModel` builds the real ticker internally because its constructor is already at Detekt's parameter limit (it likewise derives `CareLogRepository`/`RepottingOverviewPreferences` from `database`/`dataStore` rather than taking them). The chip row **is** the saved threshold (`RepottingOverviewPreferences`, wired as `YaptApplication.repottingOverviewPreferences`): a tap writes DataStore and the row reads it back, so it defaults to 2+ yr and survives leaving the page and process death. Layout: Planned group on top under every chip (season + year via `repotPlanLabelRes()`, an ended plan gets a visible "· Overdue" and `OverdueRed`), then the list under a header naming the chip; rows show cover photo, name, room and "Last repotted `DateUtils.formatMonthYear`" / "Never repotted · added …". Empty states: no active plants → "add a plant" message with the chips hidden; nothing matches and nothing planned → "Nothing to repot here — nice work"; nothing matches but plans exist → Planned plus a one-line note under the list header. **Rows copy Care's tile pattern (product ADR-0056)**: tap opens Plant Detail on the Repot tab; long-press opens a `DropdownMenu` mirrored as semantics `customActions` plus an `onLongClickLabel` (`repottingMenuActions()`: Repot… / Plan repot…, Planned rows Repot… / Change plan… / Clear plan) — no inline buttons. Nothing is duplicated: Repot… reuses `CareDatePickerBottomSheet` and goes through `QuickLogUseCase.quickLog(plant, REPOT, loggedAt)` (which clears a superseded plan via `RepotPlanReset`), Plan/Change reuses `RepotPlanSeasonDialog` → `PlantRepository.setRepotPlan`, Clear plan → `clearRepotPlan` (both column-specific). Because every write runs through `RepottingOverviewViewModel.perform()` — one `Mutex` for the page's writes, the plant re-read fresh inside it, as Plant Detail does with `plantEditMutex` — a repot's full-row lifecycle reset can't put back a plan written a moment earlier; and the page moves rows in place because every input is a flow. The prompts' target ids are `rememberSaveable` and dropped when the plant leaves the page. Compose tests live in `RepottingOverviewScreenTest` (androidTest): rows are located by the `testTag` on the clickable node (`repottingRowTag()`) and group order is asserted with `positionInRoot`, following Care's `TodayScreenTest` precedent, while content assertions use text, custom actions and selected state (#420). `SettingsViewModelRepottingOverviewTest` collects the real ticker only via `first {}`, never `advanceUntilIdle()`.
