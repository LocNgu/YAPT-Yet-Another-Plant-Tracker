# Day-change triggers for date-dependent flows (#550)

**A `combine()` whose result depends on wall-clock date needs a day-change trigger, not just its other input flows** — none of the app's other flows (plant list, care logs, sort order, …) emit purely because time advances, so a `combine()` block that reads or derives "today" (e.g. `DateUtils.todayRangeMillis()`, `CareSchedule.computeStatus()`'s due/overdue math, `LocalDate.now()`) only re-evaluates on an unrelated state change, not at midnight itself (#550). `util/DayChangeTicker.kt`'s `dayChangeTicker(zone, nowProvider, maxPollIntervalMs)` is the shared fix: a cold `Flow<LocalDate>` that emits immediately, then again once per local midnight crossing, computed calendar-day (technical ADR-0013/0034), not a fixed 24h span. Feed it into the `combine()` with the value ignored (`_`); if already at the 5-flow limit of the typed `combine()` overloads, fold it into one existing flow first (`combine(existingFlow, dayChangeTicker()) { v, _ -> v }`) rather than restructuring to array-based `combine()`. Constructor-inject as `Flow<LocalDate>` defaulting to the real `dayChangeTicker()` (mirrors `QuickLogUseCase`'s `nowProvider` convention) so a test can substitute a controllable `MutableSharedFlow`/`MutableStateFlow`. `PlantListViewModel.plantsWithStatusBeforeSearch` (the DB-bound stage `plantsWithStatus` search-filters downstream, #512 — the search stage never re-reads the ticker), `CalendarViewModel.plantsWithStatus`/`plantsByDay`, and `TodayCareRepository.observeQueue()` are the three current consumers. **Never call `advanceUntilIdle()` in a test collecting the real ticker** — its `while (true) { …; delay(…) }` always re-schedules another delayed continuation before suspending, so `advanceUntilIdle()` finds infinite future work and hangs; use `advanceTimeBy(ms)` + `runCurrent()` with an explicit, bounded amount instead (`DayChangeTickerTest`). **Every `PlantListViewModel`/`CalendarViewModel` test must pass an explicit non-real ticker, even one that never touches day-change behavior at all** — a class-level `private val dayChangeFlow = flowOf(LocalDate.now())` covers the ~140 pre-existing tests that don't (`advanceUntilIdle()` inside `Turbine`'s `.test { }` block genuinely hangs against the real default ticker's `delay()`, contrary to what independent `MainDispatcherRule`/`runTest{}` schedulers might suggest); the handful of tests that exercise day-change behavior inject their own controllable `MutableSharedFlow<LocalDate>` instead. **`CalendarViewModel.plantsWithStatus`/`plantsByDay` is a two-stage pipeline sharing `today` — the trigger and its derived value must travel together as one atomic emission, not be read from two independently-updating flows.** `plantsByDay` used to be `combine(plantsWithStatus, _visibleMonth, today)`, which re-ran as soon as *either* upstream changed; at midnight `today` ticks before `plantsWithStatus` finishes rebuilding (`buildStatus()`'s suspend `careLogRepository` calls take real time), so `plantsByDay` could momentarily pair the *new* day with the *old*, not-yet-rebuilt statuses (#550 review round 2). Fixed by combining the day and its statuses into one value, `private data class StatusesForDay(day, statuses)`, built by a single `combine(allPlants, logCount, seasonalAmplitude, today) { ... -> StatusesForDay(day, statusList) }`; both `plantsWithStatus` (`.map { it.statuses }`) and `plantsByDay` (`combine(statusesForDay, _visibleMonth) { forDay, month -> ... }`) derive from that one `statusesForDay` StateFlow instead of each reading `today` on their own. Generalizes beyond dates — any two-stage `combine()` chain sharing an upstream trigger should default to "combine once, derive twice," not re-read the trigger flow at each stage. `CalendarViewModel.today` is public (not just an internal combine input) so `CalendarScreen` reads it via `collectAsStateWithLifecycle()` instead of its own `remember { LocalDate.now() }` for the day cell's `isToday` highlight and the day-sheet's "Today" title/section — a screen left composed across midnight must not keep both around indefinitely (#550 review round 3).
