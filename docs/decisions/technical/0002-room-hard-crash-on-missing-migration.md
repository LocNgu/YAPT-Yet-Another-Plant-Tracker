# ADR-0002: Hard-crash on missing Room migration instead of destructive fallback

**Status**: accepted

**Date**: 2024-01-01

## Context

Room offers `fallbackToDestructiveMigration()` as a convenience: if the database version increases but no matching `Migration` object is registered, Room drops and recreates all tables. This is tempting during early development because it avoids writing migration code.

The risk is silent data loss in production. A developer bumps the version number, forgets to write the migration, and every user's plant history is silently deleted on next app launch.

Alternatives considered:
- **`fallbackToDestructiveMigration()`**: simple, no migration code required, but destroys user data on any version mismatch.
- **Hard-crash (no fallback)**: Room throws `IllegalStateException` at startup if a version mismatch has no registered migration. Loud failure forces the developer to write a real migration before shipping.

## Decision

`PlantDatabase` is built without `fallbackToDestructiveMigration()`. Room will throw at startup if the `version` in `@Database` is bumped without a corresponding `.addMigrations(...)` registration.

The baseline schema is committed at `app/schemas/com.yapt.planttracker.data.db.PlantDatabase/1.json`.

Every future schema change must:
1. Increment `version` in the `@Database` annotation.
2. Write an explicit `Migration(from, to)` object.
3. Register it via `.addMigrations(...)` in `PlantDatabase.getInstance()`.
4. Commit the new schema JSON file generated by KSP.

## Consequences

- User data is never silently destroyed.
- The developer is forced to think about schema changes explicitly.
- If a migration is accidentally shipped without the registered `Migration` object, the app crashes on launch with a clear error message rather than deleting data quietly.
- Schema JSON files in `app/schemas/` serve as an auditable history of every database contract change.
