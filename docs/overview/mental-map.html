Field guide · offline-first Android

How YAPT grows

A cross-section of Yet Another Plant Tracker: a Kotlin/Compose app that logs care events for houseplants and learns each plant's real watering rhythm from the user's own feedback — no cloud, no accounts, everything on-device in Room.

01

The four layers, top to bottom

Read it like soil: light hits the canopy (screens) first, the trunk (ViewModels) carries state up and down, the roots (domain logic) do the real work out of sight, and everything is anchored in bedrock (Room + DataStore). There's no Hilt — YaptApplication wires every dependency by hand as a lazy singleton (technical ADR-0001).

02

Screens & how you get there

Only Plant List and Calendar sit on the bottom nav bar (product ADR-0019) — everything else is a stack push from one of those two.

Plant List

start
plant_list?restoreMessage={msg}

Home screen. Sortable/filterable PlantCard grid, quick-log buttons per card, bulk-select action bar. Entry to Add Plant and Settings.

Calendar

calendar

Month grid (Kizitonwose library, technical ADR-0017) with care-event day markers; tapping a plant's event jumps to Plant Detail.

Plant Detail

hub
plant_detail/{plantId}

The busiest screen: chart, photo gallery, care history, and (behind PLANT_DETAIL_TABS) six per-action tabs — Water, Fertilize, Repot, Photo, Custom Reminders, Issues.

Add / Edit Plant

add_plant · edit_plant/{plantId}

Name, species, room, cover photo, base watering/fertilizing intervals. Editing room triggers a watering lifecycle reset check.

Add Care Log

add_care_log/{plantId}?careLogId={id}

Manual log entry for any CareType except CHECK; also the edit surface for an existing log.

Settings

settings

Notification prefs, adaptive-watering toggle, seasonal amplitude, backup/restore, Developer Mode unlock, About/What's New.

Graveyard

graveyard

Archived (not deleted) plants, reachable from Settings. Restore surfaces a snackbar back on Plant List.

03

What's actually stored

Room database PlantDatabase, currently version 13 — every bump ships an explicit Migration plus a committed schema JSON under app/schemas/; there is no destructive fallback (technical ADR-0002).

EntityHoldsNotable rule
PlantEntityName, species, room, photo, watering/fertilizing intervals, adaptive-watering confidence + base interval, pin flags.The row every other table hangs off; archiving sets a flag rather than deleting.
CareLogEntityOne row per logged event — CareType, timestamp, note, fertilizer type, watering feedback.Same-day WATER/FERTILIZE/CHECK duplicates are rejected at the repository level; PRUNE/REPOT/NOTE/PHOTO/MIST/CUSTOM aren't.
PlantPhotoEntityGallery photos, separate from care logs so the gallery can combine both (product ADR-0013).Backup streams photo bytes rather than base64-inlining them (technical ADR-0014).
CustomReminderEntityUser-defined recurring reminders beyond water/fertilize.Child table keyed to a plant (technical ADR-0019).
PlantIssueEntityPest/disease issues, tracked on a separate axis from due-status.Renders with IssuePurple, never a due-status color (technical ADR-0020).

04

The adaptive watering engine

YAPT's actual thesis: watering intervals aren't fixed, they're a confidence-weighted model (technical ADR-0021) that moves when the user's own feedback says the schedule was wrong — and everything about how it moves is inspectable from inside the app. The full formulas, constants, and a worked example live in watering-math.html.

1

A quick-log happens

Every quick-water/fertilize surface funnels through QuickLogUseCase — the one choke point (never duplicated per-screen) that inserts the CareLog and, if adaptive watering is on, evaluates the interval.

2

Off-schedule? Ask why

CareSchedule.GAP_AGREEMENT_TOLERANCE decides "on schedule." If not, the user is asked "Why was it late?" / "Why now?" (direction-aware wording, product ADR-0030) — the answer, not the gap length, decides whether the model learns.

3

Seasonal curve applies

SeasonalWatering multiplies the learned base interval by a computed seasonal factor (hemisphere-aware) to get the effective interval actually shown and scheduled — unless the plant is pinned.

4

Every decision is logged

A WateringAdjustment row is written regardless of outcome — trigger, before/after interval, confidence delta — so "Why this date?" on Plant Detail can show real history, not a guess (product ADR-0028).

05

Cross-cutting systems

Notifications

worker/

ReminderWorker (WorkManager, daily) scans due plants and posts via NotificationHelper; BootReceiver re-schedules after reboot. Notification actions (skip / still-moist) land on SkipWateringReceiver / StillMoistReceiver, which both call back into QuickLogUseCase.

Backup & restore

.yapt file

BackupManager/BackupSerializer export the full DB (plants, logs, photos, reminders, issues, watering adjustments, settings) to a single versioned .yapt file — the only way data ever leaves the device.

Feature flags & dev mode

off by default

FeatureFlagRegistry is the single list of in-flight experiments, all defaulting false; a hidden gesture (DeveloperModeUnlock) reveals the Developer settings section and demo-data seeding (DemoDataSeeder).

Theme

ui/theme

Material 3 nature palette — Sage Green, Warm Cream, Earth Brown — plus a separate due-status axis (Ok/Warn/Overdue) and IssuePurple, which is deliberately never reused for due-status.
